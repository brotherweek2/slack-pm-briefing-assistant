# 08. 인계 (담당자 교체)

기존 개발·운영 담당자가 떠날 때 후임자가 봇을 그대로 이어받기 위한 문서입니다. 실제 계정·주소·토큰은 적지 않습니다. 계정에 묶인 설정(트리거·속성·배포·Slack 앱)의 전체 목록과 **계정이 갑자기 사라졌을 때 복구 절차**는 [09 운영 환경 스펙](09_운영환경스펙.md)에 있습니다.

> **기록만으로 되는 것과 안 되는 것:** 코드·문서·변경 기록은 이 저장소와 노션으로 충분합니다. 하지만 트리거와 중앙 봇 웹 앱은 담당자 계정으로 돌기 때문에, **계정이 삭제되면 다음 회차부터 봇이 멈춥니다.** 퇴사 전에 아래 3~5단계를 후임자와 함께 끝내야 합니다. 일상 운영은 [00 운영자 빠른 시작](00_운영자빠른시작.md), 코드 수정은 [03 개발 가이드](03_개발가이드.md)를 보세요.

### 대기 중인 일

- 판소리: `ENABLE_PANSORI_READ`를 켜고 실제 수집·DM 확인(미리보기까지 확인됨). [판소리 안내](PANSORI_SETUP.md)
- 새 PM 1명: 캘린더 연결은 체크됐지만 send_enabled FALSE(승인 여부 확인 필요).
- 퇴사자 2명: BOT_USERS send_enabled FALSE로 정리(코드상 이미 DM·메이트에서 빠짐).
- 피드백(폼 5건·버튼 👍28/👎2): 반응한 Slack 글 제외·확인 완료 표시(2명), 라운지 회의, DM으로 할 일 추가·삭제, 알림 횟수 조절 → 파트장 협의.

## 2. 무엇을 넘기나

| 구성 요소 | 설명 | 넘길 것 |
| --- | --- | --- |
| 중앙 봇 (Apps Script) | 수집·정기 DM·버튼 응답 웹 앱 | 프로젝트 소유권, 트리거, 스크립트 속성, 웹 앱 배포 |
| 캘린더 연결 앱 (Apps Script) | PM이 본인 회사 계정으로 승인하고 일정을 갱신 | 프로젝트 소유권, 웹 앱 배포(사내 전체 뷰어 공유 유지) |

| 코드 저장소 | 이 저장소(원본 번호 파일 · 테스트 · 빌드 도구) | 후임자에게 접근 권한, 또는 회사 저장소로 이전 |

원본 업무 시트는 봇이 **읽기만** 하므로 넘길 대상이 아닙니다. 인계 중에도 원본은 바꾸지 않습니다.

## 3. 인계 순서

각 단계는 **업로드 금지 시간(10:15~11:10 · 13:45~14:40 · 16:45~17:40)을 피해서** 합니다.

### 1단계 — 파일을 팀 공유 드라이브로 옮기기 (완료)

> 2026-11 완료. 다시 옮길 일이 생기면 아래 원칙을 지킵니다.

1. 중앙 봇 · 연결 앱 · 봇 시트 3개를 공유 드라이브로 **이동**합니다. **복사하지 않습니다.** 복사하면 스크립트 ID·시트 ID가 바뀌어 속성·배포 주소가 모두 어긋납니다.
2. 초기 사본 파일 3개는 선택(옮기지 않아도 운영에 지장 없음).
3. 다음 정기 회차의 관리자 요약 DM이 정상으로 오는지 확인합니다.

### 2단계 — 후임자 접근 확인

- 후임자가 **본인 회사 계정**으로 세 파일을 편집할 수 있는지 확인합니다.
- 파일 접근권만으로는 트리거가 넘어가지 않습니다. 트리거는 **설치한 계정의 권한**으로 돕니다.

### 3단계 — 실행 계정 전환 (기존·후임 함께, 한 번에)

중복 발송을 막기 위해 아래 순서를 지킵니다.

1. **기존 담당자**가 중앙 봇에서 `removePersonalBriefingTriggers`로 정기 DM 트리거 3개를 지우고, Apps Script 트리거 화면에서 `collectBbpmSnapshot`(수집) 트리거도 지웁니다.
2. **후임자**가 중앙 봇에서 `pinBriefingExecutor`를 실행해 실행 계정을 본인 회사 계정으로 고정합니다(`BRIEFING_EXECUTOR_EMAIL`).
3. **후임자**가 `installBbpmCollectTrigger`(수집 1개)와 `installBriefingTriggers`(발송 3개)로 트리거를 본인 계정에 만듭니다.
4. `previewBriefingAutomationStatus`로 트리거 4개와 수집 시각을 확인합니다.
5. `PILOT_PM_NAME`(관리자 요약·시험 DM 수신자)을 후임자 이름으로 바꿉니다. 설정은 봇 시트 BOT_SETTINGS → `applyBotSettings`로 반영합니다(반영 후 B열이 비는 것은 정상).

### 4단계 — 웹 앱 재배포 (주소 유지)

- 중앙 봇(버튼 응답)과 연결 앱 모두 **같은 배포 ID로** 새 버전을 배포합니다: `clasp deploy -i <기존 배포 ID>`. 새 배포를 만들면 주소가 바뀌어 Slack 버튼과 PM 연결 링크가 끊깁니다.
- 실행 사용자를 후임자로 바꿔야 하면 후임자 계정에서 배포합니다.
- 연결 앱 주소는 중앙 봇 속성 `CALENDAR_CONNECT_URL`에 들어 있습니다. 주소가 바뀌었다면 이 값도 바꿔야 합니다.

### 5단계 — Slack 앱

- 후임자를 Slack 앱 협업자로 추가합니다.
- 토큰은 BOT_SETTINGS로 반영할 수 있습니다(`SLACK_BOT_TOKEN`, xoxb- 형식만). 토큰을 문서·저장소·채팅에 적지 않습니다.
- 앱을 재설치하면 토큰이 바뀔 수 있으니 재설치 후에는 반드시 다시 반영합니다.

### 6단계 — 확인하고 마무리

- [ ] 후임자 계정 기준으로 세 회차 연속 관리자 요약이 정상
- [ ] PM 1명 이상이 실제 DM·캘린더 자동 갱신·버튼(완료·점심 메이트·피드백)을 확인
- [ ] `previewBriefingHealth`에서 실행 계정 검사 통과
- [ ] GitHub 비공개 저장소에 후임자 협업자 추가(또는 회사 계정으로 이전), 노션 기록 접근 확인
- [ ] 위 확인 후 기존 담당자의 편집 권한·Slack 앱 권한 정리

## 4. 코드를 이어서 고칠 때

- 원본은 `apps-script-linked/`의 번호 파일입니다. Apps Script에는 `node tools/build-apps-script.cjs`로 만든 7개 합본(`apps-script-deploy/`)만 올립니다.
- 순서: 원본 수정 → `node tools/test-local.cjs` 전체 통과 → 빌드 → 원격을 내려받아 직전 업로드본과 같은지 확인 → `apps-script-deploy/`에서 `clasp push` → 다시 내려받아 일치 확인.
- `clasp push`가 성공하고 재조회가 일치한 **뒤에만** `clasp deploy`를 합니다. push가 막힌 상태에서 deploy만 되면 옛 코드가 배포됩니다.
- 이 저장소로 공개본을 갱신하는 스크립트가 토큰이나 실제 식별자를 감지해 멈추면, 그 상태로 커밋하지 않습니다(실패를 무시하고 커밋해 대량 삭제가 올라간 적이 있음).
- 여러 AI 에이전트(Codex·Claude)가 같은 폴더를 동시에 고친 적이 있습니다. 작업 전 원격과 git 상태를 먼저 확인하고, 한 번에 한 사람(에이전트)만 업로드합니다.

## 5. 하지 않을 것

- 원본 업무 시트의 수정(셀·서식·탭·권한 등 전부). 양식이 바뀌면 봇의 읽기 코드를 고칩니다.
- 파트장 승인 없이 발송 함수(`sendScheduledBriefing11/14/17`, `resumeConnectedBriefingSend`) 실행.
- 발송 기록·점유 속성을 지워서 재발송 시도.
- 토큰·키·원본 시트 주소를 문서·저장소·노션에 저장.
